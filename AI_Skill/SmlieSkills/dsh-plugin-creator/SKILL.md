# DSH 插件开发

开发 DeepSeek Harness（DSH）插件，先确定交付形态，再核实目标版本的真实接口。覆盖需求设计、实现、调试、验证、打包与部署准备。

## 触发条件

- 创建或维护 DSH 插件、工具、服务、事件监听、客户端界面与主题。
- 调试插件激活、依赖注入、回放、构建和安装问题。
- 用户指定 `dsh-plugin-creator`，或使用旧称 `deepseek-harness-plugin-creator`。
- 普通 Agent 技能文档、其他平台的插件、DSH 内核本身的修改，不属于本技能的插件开发流程。

## 按交付形态选择流程

| 用户目标或现有项目 | 开发形态 | 按需读取 |
| --- | --- | --- |
| 可安装、可分发、跨进程保留的插件；已有包源码与构建配置 | 可安装插件包 | [插件包开发](references/package-development.md) |
| 当前 DSH 会话中的临时功能；使用 `cordis_define` / `cordis_run` | 会话内动态插件 | [动态插件开发](references/cordis-dynamic.md) |
| 修改 `@pluginId`、修复或回滚已有动态版本 | 既有动态插件 | [动态插件开发](references/cordis-dynamic.md)中的版本流程 |
| 激活、数据、界面、回放或安装异常 | 沿用原有形态 | [故障定位](references/failure-atlas.md) |

用户未指定时，从现有项目和目标生命周期判断；仍无法判断且会改变交付方式时再询问。不要因一种流程遇到错误就擅自切换形态。

动态代码的纯 JavaScript、无模块导入等限制只适用于动态求值环境。可安装包根据实际构建工具使用 TypeScript、模块和客户端构建。动态流程的工具不可用时，列出缺少的能力，保留当前方案并说明需要在提供这些工具的 DSH 环境运行；不可伪造查询或执行成功。

## 共同工作规范

1. **读取目标环境**：确认 DSH 版本、运行配置、插件现状和同版本示例。动态插件先查询当前能力目录；插件包先读包配置、官方对应版本文档与实现。文档快照不能代替运行时接口。
2. **定义职责**：区分 Host（宿主端）与 Client（客户端），确定数据所有者、硬依赖、可选能力、界面入口及交付结果。优先复用已有数据和窄范围扩展点。
3. **管理生命周期**：`apply(ctx)` 注册能力；事件、工具、界面、计时器和外部订阅必须有受 Cordis 管理的清理路径。缺少硬依赖时等待激活，可选能力缺失应降级。
4. **分离业务与展示**：业务返回值保持类型正确、无损且可供程序使用；模型文本、界面摘要和持久化事件分别限制大小。只从内部实时对象读取必要字段，再构造自己拥有的 JSON。
5. **按需验证**：覆盖本次涉及的运行模式和安装边界；用真实挂载、卸载、浏览器交互或回放验证相应行为。静态检查不能证明真实宿主兼容。
6. **遵循项目标准**：说明、界面和代码注释使用中文，文件名与代码标识符使用英文；发布版本采用语义化版本。外部发布、审批和运行权限沿用用户授权及目标平台机制。

## 使用示例

- “创建一个可安装的 DSH 查询插件”：选择插件包流程，核实工具契约、构建入口和配置挂载，再实现与安装验证。
- “在当前会话添加临时状态卡片”：选择动态流程，发现工具并查询客户端插槽后定义、运行。
- “修改 `@pluginId` 的按钮”：先读取原 Package（代码版本）和诊断，保留另一端代码，在原 Plugin（插件实例）下新增版本。
- “动态插件更新失败，恢复旧版”：读取当前版本指针与诊断，对 `currentPackageId` 使用 `run`；不能把失败状态当成已经回滚。

## 验证与交付

交付说明应包含选用的开发形态、版本与接口依据、实际修改、使用方法、已验证结果及尚缺的宿主条件。

- 插件包：说明依赖、标准结果与各展示层、实际测试过的直接调用/代码模式/回放/界面、独立配置安装结果。
- 动态插件：说明 `pluginId`、`packageId`、本次运行状态、更新或恢复结果。`waiting`、`starting` 和 `awaiting-approval` 均不表示已成功运行。
- 没有运行工具、浏览器或目标宿主时，只报告已完成的文件和静态校验，不宣称技能已被实时发现或插件已通过运行测试。

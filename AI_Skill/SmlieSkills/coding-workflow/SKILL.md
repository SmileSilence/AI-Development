# AI 编码工作流与代码规范

本技能提供 AI 辅助编码的完整工作流程，以及一套通用的代码规范、编码标准和代码风格指南，帮助开发者高效、一致、可读地完成软件开发。

## 触发条件

### 自动触发
- 用户请求用 AI 编写、生成、补全、审查、重构代码，或编写单元测试、修复 bug
- 用户要求按完整流程推进：需求分析 → 提示设计 → 代码生成 → 审查 → 测试 → 交付
- 用户请求格式化代码、统一代码风格、整理代码结构
- 用户询问命名规范、注释规范、region 划分、错误处理等编码标准
- 用户请求代码审查、规范检查、风格一致性检查
- 用户说「AI 帮我写代码」「用 AI 编码」「AI 辅助开发」「AI 编码流程」「code-style」「代码风格」「代码规范」
- 编码、生成、重构流程中编写代码时（本技能为通用规范，普遍适用）

### 适用范围（通用规范）
- 本技能是通用代码规范，**普遍适用于所有编码、生成、重构流程**，不仅限于规范审查场景
- 引擎/框架特有规范（如 UE、Unity）优先：与特有规范冲突时遵循特有规范；不影响特有规范的部分，仍须遵循本技能通用规范
- 语言特定规范（如 PEP 8）优先：语言规范更具体时以语言规范为准，未覆盖部分遵循本技能通用规范

### 不触发（避免误用）
- 仅讨论编码概念而无实际编写任务 → 不激活本技能
- UE / Unity 引擎项目的开发任务 → 不激活本技能

## 核心原则

- **明确需求**：清晰定义问题和期望结果
- **迭代优化**：通过多次交互逐步完善代码
- **质量保证**：始终验证AI生成的代码质量
- **一致性**：遵循项目或团队已有的代码风格
- **可读性**：编写易于理解、维护的代码
- **简洁性**：避免不必要的复杂性

## 工作流程

### 1. 需求分析
- 理解用户需求和业务背景
- 确定技术约束和性能要求
- 明确输入输出规格
- **明确交付要求**：确认项目输出/打包文件需配套使用文档，项目需自带帮助（help）

### 2. 提示设计
- **具体明确**：提供详细的上下文和要求
- **分步骤**：将复杂任务分解为多个简单步骤
- **示例驱动**：提供输入输出示例
- **约束说明**：明确技术栈、性能要求等限制

### 3. 代码生成
- 使用AI生成初始代码框架
- 逐步细化和完善实现
- 保持代码模块化和可测试性
- **异步调用注意**：编写代码时注意异步调用，检查是否有同步调用在使用异步调用里的数据（返回值/变量），避免时序竞态导致取到未完成、`null/undefined` 或旧值

### 4. 代码审查
- **语法检查**：确保代码无语法错误
- **逻辑验证**：检查算法和业务逻辑正确性
- **异步数据一致性**：检查是否存在同步调用（普通方法/事件/回调/属性读取）直接消费异步调用返回的数据；若有，必须改为在异步结果就绪后（`await`/`.then()`/回调内）再使用，防止拿到未完成或空数据
- **性能分析**：评估时间和空间复杂度
- **安全审查**：检查潜在的安全漏洞

### 5. 测试验证
- 编写单元测试和集成测试
- 验证边界条件和异常情况
- 进行性能测试和压力测试
- **覆盖优先级**：关键路径优先覆盖——核心业务逻辑、边界条件、错误路径

### 6. 迭代优化
- 根据测试结果调整代码
- 优化性能和可读性
- 重构和改进架构

### 7. 交付
- **使用文档**：项目输出/打包文件（安装包、构建产物、发布包等）必须编写对应的使用文档，说明安装、配置、运行和使用方法
- **帮助系统**：项目需自带帮助（help），帮助形式根据项目自行设计（命令行帮助、帮助菜单、内置帮助页等），必须包含使用说明

## 代码规范

### 命名规范
- 使用有意义的变量名、函数名和类名
- 变量名使用小写字母和下划线（snake_case）或小驼峰（camelCase），根据语言约定
- 常量使用全大写和下划线（UPPER_SNAKE_CASE）
- 类名使用大驼峰（PascalCase）
- 命名风格选择依据：
  - 小驼峰（camelCase）：第一个单词小写，后续单词首字母大写，如 `firstName`、`getUserName`
  - 大驼峰（PascalCase）：所有单词首字母大写，如 `FirstName`、`GetUserName`
  - 蛇形命名（snake_case）：所有字母小写，单词间用下划线连接，如 `first_name`、`get_user_name`
  - 大写蛇形命名（UPPER_SNAKE_CASE）：所有字母大写，单词间用下划线连接，常用于常量，如 `MAX_VALUE`、`DEFAULT_TIMEOUT`
- 根据编程语言的惯例选择命名风格，保持项目内部一致性，遵循团队或社区的编码规范

### 代码格式
- 使用一致的缩进（空格或制表符，根据项目要求）
- 每行代码长度建议不超过 80-120 个字符
- 使用空行分隔逻辑块

### 注释规范
- 为公共 API、复杂算法和业务逻辑添加注释
- 使用文档字符串（docstring）描述函数、类和模块
- 避免无意义的注释，代码应自解释

### 代码区域划分（region）
- 使用 region 标记区分代码块/功能块，增强可读性并支持编辑器折叠与跳转
- region 名称应简洁明确，描述该块的功能，如「初始化」「事件处理」「工具函数」
- 每个代码块/功能块必须以 region 开始标记开头、结束标记收尾，确保成对匹配
- region 语法随语言而定：
  - Lua：`--#region` / `--#endregion`
  - C#、C/C++、JavaScript：`//#region` / `//#endregion`
  - Python（部分编辑器）：`#region` / `#endregion`

### 错误处理
- 使用适当的异常处理机制
- 避免空的异常捕获
- 提供有意义的错误信息
- **异步数据一致性**：注意异步调用，确保没有同步调用（普通方法/事件/回调/属性读取）在使用异步调用里的数据；数据须在异步结果就绪后（`await`/`.then()`/回调内）再使用，防止拿到未完成或空数据

### 防御编程
- 外部输入必须校验类型和边界，拒绝非法数据进入业务逻辑
- 文件操作使用语言的标准路径 API（如 Python 的 pathlib.Path），避免字符串拼接路径
- 平台特有逻辑显式判断并附 fallback（如 Windows 使用 `sys.platform == "win32"` 判断）

## 语言特定规范

### Python
- 遵循 PEP 8 规范
- 使用类型提示（type hints）
- 使用文档字符串（Google 或 NumPy 风格）

### C/C++
- 遵循 Google C++ Style Guide 或项目特定的规范
- 使用头文件保护（#ifndef 或 #pragma once）
- 命名约定：变量和函数使用 snake_case，类名使用 PascalCase，常量使用 UPPER_SNAKE_CASE
- 明确内存管理，避免内存泄漏
- 使用 RAII（资源获取即初始化）管理资源
- 避免使用裸指针，优先使用智能指针（如 std::unique_ptr, std::shared_ptr）
- 使用 const 正确性
- 遵循 C++ 核心指南

### C#
- 遵循微软 C# 编码规范
- 使用 PascalCase 用于类名、方法名、属性名和公共成员
- 使用 camelCase 用于局部变量和参数
- 使用属性（Properties）而不是公共字段
- 使用 var 进行类型推断（当类型明显时）
- 遵循 LINQ 最佳实践
- 使用 async/await 进行异步编程
- 使用依赖注入（DI）和控制反转（IoC）
- 遵循 SOLID 原则

### Lua
- 使用 snake_case 用于变量和函数名
- 避免使用全局变量，优先使用 local 关键字
- 使用 LuaDoc 或 LDoc 进行注释
- 遵循 LuaRocks 风格指南
- 使用模块化组织代码
- 避免使用复杂的表构造，保持简洁
- 使用元表（metatable）进行面向对象编程时，保持清晰
- **跳转标记**：按文档要求添加跳转标记（如 `--! 标记名`），便于在编辑器中快速定位到对应代码位置，具体语法以项目文档为准
- **代码区域**：使用 region 标记（`--#region` / `--#endregion`）区分代码块与功能块，每个功能块成对包裹

## 最佳实践

### 决策和确认规则
- **设计部分**：架构设计、模块划分、接口设计等需要用户确认后再实施
- **bug修复**：直接修复bug，无需用户确认，但修复后需向用户报告修复内容和测试结果
- **优化结构**：代码重构、性能优化、结构调整等需要用户确认后再实施
- **报告机制**：所有操作完成后需向用户报告结果和影响

### AI 助手行为规范
- **主动探索**：任务涉及多文件时，先浏览代码库理解上下文再动手，不凭记忆猜测
- **逐项推进**：复杂多步任务按顺序推进，每步完成再进入下一步
- **不可逆操作确认**：涉及删除、覆盖、外部发布等不可逆操作前，先确认再执行
- **工具使用**：优先使用专用工具（Read、Grep、Glob、Edit、Write）而非 shell 命令；文件搜索用 Glob，内容搜索用 Grep；不重复读取刚编辑过的文件来验证修改
- **报告结果**：失败如实汇报错误信息；跳过说明原因；完成说明验证依据

### 提示工程技巧
- 使用角色设定（如"资深Python开发者"）
- 提供代码上下文和项目结构
- 指定代码风格和规范
- 要求AI解释其推理过程

### 代码质量保证
- 始终验证AI生成的代码
- 不要盲目接受AI建议
- 保持对代码的理解和控制
- 结合人工审查和AI辅助

### 工具集成
- 与版本控制系统（Git）集成
- 使用代码质量检查工具
- 集成自动化测试框架
- 配置持续集成/持续部署（CI/CD）
